# Defense and mitigation

CONFIRMED_FROM_CODE: the traced Active final-damage function has target multipliers and flat additions but no target DEF division. BattleUnitBase.BeHit then handles block/shield, immunity, limits and death resistance. This does not prove that DEF is irrelevant to every skill expression or status.

CONFIRMED_FROM_DATA_AND_CODE: BattleApi contains `def`, `def_per`, and BattleDefForce = ceil(TargetCmdOwner.def * (1 + TargetCmdOwner.def_per/100)). `TargetCmdOwner` is the source that owns the command, so this is source defense strength rather than target mitigation.

## Catalog consumer inventory

`tools/audit_defense_consumers.py` traces DEF-derived skill arguments into command-effect parameters for the resource-144 and current resource-150 PC catalogs. It records only derived routes and source hashes in `research/evidence/defense-consumer-audit.json`; it does not publish the underlying tables.

Both builds contain 358 skills with at least one DEF-derived argument. The inventory finds 490 variant-specific consumer routes in resource 144 and 492 in resource 150:

| Use | resource 144 | resource 150 |
| --- | ---: | ---: |
| Shield | 330 | 335 |
| Summon | 79 | 79 |
| State | 77 | 74 |
| Heal | 3 | 3 |
| Damage | 1 | 1 |

The sole damage route is identical in both builds: skill 147434, `深空回响(未完成)`, variant 1000, command 1880 row 2, where argument 1 enters `BEActiveDamage`. The catalog marks the skill unfinished. This proves only that source DEF can enter one catalog damage base; it does not prove that the skill is accessible or executable in normal play. No damage command row directly reads a DEF expression.

Combined with the traced Active final-target and BeHit paths, this audit found no universal target-DEF divisor. Indirect state effects and mechanics outside the inspected paths remain possible.

Normal shield resolution subtracts available block from incoming damage and reduces block accordingly. Puncture branches reduce block while retaining damage. The resolver returns a surprising negative blockedDamage diagnostic when block exceeds damage; retain and verify this behavior before using that diagnostic for totals.

Other layers include five spellbound reductions in offensive computation, target damage-taken factors, damage immunity, a remaining damage-limit budget, active-damage HP thresholds and death resistance. They cannot be collapsed into one guessed DEF formula.

## Runtime-checked intermediate hit helpers

`engine/hit-limits.mjs` matches 282 copied-original BattleUnitUtil cases, generated by `tools/hit_limits_oracle.py` and compared in `tests/hit-limits.test.mjs`. It accepts explicit nonnegative properties and a living target, exposing diagnostic intermediate values rather than final damage.

The traced BeHit order is immunity selection, shield resolution, optional retained-HP threshold, incoming damage budget, death-resistance adjustment, HP subtraction, then recorded/event/death handling. The adapter covers only the three numerical helpers from shield through incoming limits. Immunity and active-prevention eligibility remain external inputs/decisions; HP mutation and callbacks are not executed.

- Ordinary damage consumes shield and sends the remainder onward. Puncture consumes shield but keeps the incoming damage amount. The helper ceilings the damage remainder, while shield loss can retain a fraction.
- When ordinary shield exceeds incoming damage, the original blockedDamage diagnostic is incoming minus shield, a negative number. The shield loss is a separate positive field. Tests preserve this behavior rather than silently repairing it.
- With active-prevention eligibility and a positive retained-HP threshold, the request is limited to max(0, current HP minus threshold). The converted portion is recorded before later budget limits.
- Positive be_damage_limit restricts the request to max(0, limit minus be_damage_statics). These helpers do not increment the statistics themselves; do not invent per-hit budget updates.
- A positive pvp_death_resist property clamps a lethal request to HP minus one. The helper itself checks the property, not the current game mode. This does not establish how or when that property is installed, consumed or restored.

The API returns finalDamage null. Real HP subtraction, property floors, immunity, state callbacks, damage events and death execution still require integration and gameplay validation. The tests do not convert the observed Frenzy record into a completed fixture.

The remaining-limit expression does not imply a universal consumable budget. [DAMAGE_CAP_LIFECYCLE.md](DAMAGE_CAP_LIFECYCLE.md) distinguishes an HP-change-driven phase counter from per-hit caps. Preserve mechanic-specific updates between hits rather than automatically adding every incoming hit to be_damage_statics.
