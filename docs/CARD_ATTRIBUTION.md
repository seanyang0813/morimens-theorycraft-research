# Card copying and source attribution

Recovered scope: PC resource 144 / build 51. Code plus bounded original-runtime request evidence; selected replay instance ownership is not yet reconstructed.

Moxia skill 122483 (Human Explosion) is both Card_Skill and Card_Strike. Command 122499 deals its Active damage, then at potency greater than one selects a history Strike using `GetCopyHistoryCard({Card_Strike},0,99,1,0,0,{123811,124733})`, creates a hand card, and adds states 2948, 2454 and 2983. State 123811 marks Human Explosion itself. The selector's exclusion arguments must not be mistaken for damage or ownership modifiers.

`BattleCardMgrServer.InsertBoutHistory` stores the played card's skill ID, level, camp, special-owner UID, performSkillId and card types. `GetHistoryCard` reconstructs a temporary NoneDeck card from those fields. `BECreateCard` subsequently copies the selected card's ID, level, special owner, performSkillId and types into AddNewCard. Its generating command's castRoleUid is also passed as separate creation metadata, while the `owner` field is the selected card's special owner.

`tools/create_card_oracle.py` now executes the original protected `BECreateCard.DoEffect` against a synthetic card-manager observer. The observed request boundary confirms that a count of 2.2 becomes three descriptors, each descriptor keeps the selected card's ID and level, an omitted show flag becomes true, zero becomes false, and omitted explicit arguments fall back to `target.createCardArgs`. The request separately carries `castRoleUid`, the deck expression's camp, the selected card's special owner, `performSkillId`, card types and the parsed top/bottom placement. `BECreateCard` also replaces its own target list with cards returned by `AddNewCard`. `engine/create-card-command.mjs` reproduces this bounded request construction and stops before `AddNewCard` mutates a deck or fires triggers.

Agents can run the boundary with `node tools/run_create_card_command.mjs research/examples/create-card-command.json`. The result is a list of auditable `AddNewCard` requests plus explicit unresolved dependencies; it is not a finished card-sequence simulation.

The next boundary is also tested. `tools/add_new_card_oracle.py` executes original `BattleCardMgrServer.AddNewCard`. Normal generated cards are inserted into the requested deck and returned to the caller. Top insertion repeats at index one, so two created cards appear in reverse creation order. A card created while the hand is at capacity is still constructed, stored in `NoneDeck`, reported through `OnAddNewCard` and a `NoneDeck`-to-`NoneDeck` record, but it is not returned as a playable new card and receives no ordinary `CardDeckChange` request. Eternal card UIDs are tracked even when the creation branch changes deck. Dimension-card creation exits without constructing anything during an extra bout. Ordinary Dimension capacity and random insertion remain unresolved.

`tools/card_owner_oracle.py` executes original `BattleCardServer.InitOwner` across six branches. For a skill with `AwakerID`, a special owner wins without an Awakener lookup. Otherwise the configured Awakener is used when present. If that Awakener is absent, `fromCardUid` can supply the source card's owner and also replaces `performSkillId` with the source card's value; the player is the final fallback. A skill without `AwakerID` uses the player and ignores a supplied special owner. `InitCmdServer` uses the resolved `owner.uid` as `castRoleUid` and the card's skill ID as `skillConfigId`.

`BattleCardServer.InitCmdServer` is now tested at its constructor boundary. It creates an optional pre-command first, then the main command. Both requests copy skill level, skill ID, card UID, resolved owner as `castRoleUid`, and a deep clone of the card arguments; only the pre-command receives `isPreCmd=true`. The main command then runs `GetSkillArgs`.

`engine/generated-card-pipeline.mjs` composes creation, tested Draw/Hand placement, owner resolution, command-constructor requests and the main command's tested `GetSkillArgs` normalization without mutating its input. Its command plans expose the resulting `Arg1...ArgN` bindings: raw base arguments are ceiled first, then copied card arguments replace matching positions. Run the isolated explicit-input mode with `node tools/run_generated_card_pipeline.mjs research/examples/generated-card-pipeline.json`. BECreateCard, BattleCardMgrServer and BattleCardServer are byte-identical in resource 150; executing all 21 inherited generated-card fixtures with current BattleConst and BattleLogicEvent also matches exactly, while argument normalization is covered by the separately tested current skill-argument boundary. Explicit mode requires the caller to supply the command and raw base arguments; catalog mode derives them under the constraints below. The pipeline stops before `BattleCmdServer` constructor internals, card-state initialization, card-entry listeners and generated-card execution.

`engine/catalog-card-command-plan.mjs` removes that manual argument step for supported numeric catalog skills. It resolves the card `tid` through hashed Skill, BattleApi and Cmd exports, selects its command and progression fields, evaluates the growth and parameter expressions against explicit live variables/state queries, applies copied arguments through the same command-plan boundary, and retains every ordered command row. The catalog declares its build and must match the request. A real resource-144 Arachne Strike fixture resolves command 133374 and base arguments `[100,5,2]` at supplied attack 1000 and state layer 2; a copied first argument of `0.5` produces `[0.5,5,2]`. Its plan retains all four effects in order: Active damage, ultimate-energy gain, conditional attached action and player state addition. The full creation-to-plan example runs with `node tools/run_catalog_generated_card_pipeline.mjs research/examples/generated-arachne-catalog-pipeline.json`. This is a pipeline fixture, not a gameplay damage claim, and missing live inputs fail closed. Command rows are not executed at this boundary.

Therefore an ordinary copied Arachne Strike can still execute under Arachne even if Moxia generated the copy. Copying alone does not transfer its attack calculation to Moxia. A special-owner override is an explicit exception and must be established for the actual card. The path also retains performSkillId separately, so animation identity must not be substituted for the logical owner without checking the rendering path and actual instance.

`BattleStatsMgr.ProcessRoleStats` credits skill-origin damage to cmdServer.castRoleUid. `BattleStatPackMgr.AddBattleStatPackSkillStats` records that role and cmdServer.skillConfigId in the turn bucket. State-origin damage instead goes through state ownership allocation. Thus a character/source statistics entry establishes the recorded role/skill bucket; it does not by itself establish the number of uses, whether the card was copied, or its modifiers at impact.

For replay-002, the Arachne Strike 2205 entry remains stronger attribution evidence than the character animation visible alongside a floating 6615. The latter may be a preceding event's number or an overridden presentation. Neither explanation is proved yet. Capture the actual card and complete event boundary before assigning the frame to a single hit.

`tools/history_card_oracle.py` now executes the original protected `BattleCardMgrServer:GetBoutHistoryCard` against reconstructed history cards and state observers. Seven fixtures prove that traversal starts with the newest card in the newest included bout, non-Strike cards are skipped, excluded types and duplicate skill IDs are honored, and a candidate carrying either excluded state 123811 or 124733 is skipped in favor of an older eligible Strike. If every matching Strike carries an excluded state, selection returns no card. `engine/copy-history-card-selection.mjs` reproduces those fixtures and exposes the bounded selector through the theorycraft API as `select-copy-history-cards`.

This closes the selector ambiguity only. The caller must still reconstruct the actual history cards and state IDs at the command boundary. Selection does not create the copied card, bind `LastTarget`, attach states 2948/2454/2983 or execute the resulting card, and it does not establish an observed replay sequence.

Those later boundaries now have separate evidence. Original `LastTarget` fixtures return the previous effect's target list, and the creation fixtures prove that this list becomes the cards returned by `AddNewCard`. Hand overflow constructs a card in `NoneDeck` but returns no playable card, leaving the later state rows with no target. Connected original Card-state fixtures store `card_cost = -1`, `consume = 1` and `nothingness = 1` for states 2948, 2454 and 2983; the installed resource-150 modules reproduce all three. `run-mortal-blast-copy-suffix` composes these proven pieces after a caller proves the potency condition. The composition still does not execute one connected scheduled command, its event listeners or the copied Strike.
