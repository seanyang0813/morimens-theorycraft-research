# Live numeric command expressions

`engine/command-expressions.mjs` exports `compileNumericCommand(expression)`. It parses a restricted numeric Lua expression into an authored expression tree and returns a reusable evaluator. Each evaluation takes `readVariable(name)` and returns `{values,reads}`. Values are the comma-separated parameter list; reads record each variable value in evaluation order. No JavaScript eval, Lua runtime or original game code is shipped in this module.

Supported syntax: finite decimal/scientific numeric literals, identifiers and dotted property names, parentheses, unary minus, addition, subtraction, multiplication, division and comma-separated values. Numeric literal inputs are also accepted. It preserves operation order and reevaluates variables each time. Unknown/nonfinite values throw. Comparisons, booleans, strings, indexing, comments, exponentiation and other operators are explicitly unsupported. A caller must resolve variables; dotted names do not automatically traverse arbitrary application objects.

Function calls require an explicit compile-time `allowedFunctions` array and an evaluation-time `callFunction(name,args)` binding. Numeric arguments, including nested calls, evaluate in order; results must be finite numbers. Every call is recorded in the returned `calls` list with its arguments and result. There are no built-in arbitrary object methods or implicit math functions. Bindings should be read-only state queries; the evaluator does not enforce purity of caller-provided JavaScript callbacks. Missing bindings, unknown calls and unsupported return types throw.

`tools/state_query_expression_oracle.py` executes the original compiled parameter expression used by skill 4638 / 57342, with numeric attack/growth and supplied GetStateLayer adapters for states 45713 and 119813. Sixteen cases match both result values and query order. This confirms that expression's arithmetic and calls, not the original state lookup or skill selection. A scheduled composition test changes a state in a child effect and observes different damage parameters on later hits.

`tools/numeric_command_expression_oracle.py` executes six original FuncTable closures with four supplied numeric environments each. The 24 fixtures cover Arg1, two-argument lists, the active-damage parameter tuple, caster max HP, target physique scaling and attack-times-growth multiplication. This evidence covers those closures only, not the entire parser grammar or original environment lookup. Separate authored tests check arithmetic precedence and rejection boundaries.

A composition test connects the evaluator to `resolveCommandArgument`, `enqueueActiveDamage` and `ResearchEffectOrder`. A generated child changes state after each hit; later Arg1 fallbacks see the new value, while the initialized repeat count and parameter bonus remain fixed. The damage resolver in this test is synthetic. This verifies integration behavior, not full original command execution or gameplay damage.

Conditional expressions now use the separate `compileCommandCondition` API; see COMMAND_CONDITIONS.md. Row execution and target resolution remain unfinished. Do not treat successful parsing of a damage parameter as evidence that its containing skill is supported.
