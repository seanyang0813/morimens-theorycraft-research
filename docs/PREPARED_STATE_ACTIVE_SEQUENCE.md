# Prepared state-to-Active sequence

`run-prepared-state-active-sequence` connects two catalog-backed theorycraft operations. It executes one supported role-state card, binds its recipient to the caster of a later prepared Active card, carries changed numeric role properties and explicitly declared `CmdCaster.GetStateLayer` values, then executes the Active card from that updated snapshot.

The singular operation supports resource 144, resource 150 and the installed resource 151 build. Resource 151 is bounded by 432 direct state/property mutation matches, zero mismatches, unchanged Skill/Cmd/State/BattleApi/Constant catalogs and the separately supported narrow Active adapter. The internal state execution profile applies only through the singular handoff. Its ordered chain also supports resource 151 when every Active action uses schema 1 or 4; the general role-state command and paid chain remain pinned to resource 144/150.

The caller supplies both cards' progression and runtime inputs, the initial role registry, a complete Active snapshot and one explicit role binding. The engine loads Skill, BattleApi, Cmd and State rows from one pinned build. It rejects mismatched builds, different state-recipient and Active-caster identities, missing recipients, nonnumeric property changes and any pre-state property or declared layer that disagrees with the Active snapshot.

The example in `research/examples/theorycraft-prepared-state-active-sequence.json` uses exported skill 134203 and state 3835. `research/examples/theorycraft-installed-prepared-state-active-sequence.json` exercises the same bounded handoff against the installed resource-151 catalogs. A recipient with `i_crit_damage_per = 50` stores the state's 70-point contribution and receives a 105-point live `crit_damage` addition. That updated role then casts exported skill 3997. With the example's explicit 100% critical chance and roll, its one-point base hit becomes three damage after the recovered critical rounding path. The number is a small integration fixture, not a build recommendation.

This boundary carries one state card into one Active card. It does not infer party/player proxy routing, costs, card zones, target selection, state duration or expiry, callbacks, other actors, target-state mutations or reactive effects. It remains an experimental theorycraft result with `finalDamage: null`; it is not cheese evidence or independent gameplay verification.

`run-prepared-state-active-chain` extends the same checked handoff to a nonempty ordered list of prepared Active skills. On resource 151 it accepts only prepared Active schemas 1 and 4; schemas 2 and 3 fail closed until their joined energy/multi-target boundary is separately proved. Every action template must describe the same pre-sequence target, caster and target binding. The engine applies the state mutation to each caster snapshot, threads resulting target HP and Block into the next action, and carries ultimate energy whenever the prepared action exposes it. It stops before actions after an incomplete or lethal result. `research/examples/theorycraft-prepared-state-active-chain.json` executes five catalog-backed Active cards and exposes each transition; `research/examples/theorycraft-installed-prepared-state-active-chain.json` runs the same bounded sequence on resource 151; its deliberately tiny values are an integration fixture.

`run-paid-prepared-state-active-chain` places ordinary non-keeper PvE play checks and energy payment before that state card and every Active card. It prevalidates all resource and effect inputs, requires distinct card instances, suppresses a rejected card and every later effect, preserves payment for a lethal card, and does not pay cards after death. `research/examples/theorycraft-paid-prepared-state-active-chain.json` starts with six energy, pays one for each of six accepted cards, and finishes with zero energy and the same five-card damage trace.

That exact request shape can pass through the gameplay-prediction freezer. Its scenario-scoped runtime contract pins the complete imported engine dependency graph plus SHA-256 hashes of the Skill, BattleApi, Cmd and State files used for the selected build. Replay fails if the request, a relevant engine module or one of those catalog files changes. This makes a future before-outcome calculation auditable; the included tiny example remains synthetic and earns no gameplay or holdout credit.
