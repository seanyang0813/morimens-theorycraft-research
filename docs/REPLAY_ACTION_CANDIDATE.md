# Replay action regression candidate

`tools/build_replay_action_candidate.mjs` converts one hit inside an indexed `UseCard` boundary into the existing complete battle-property snapshot scenario. By default it reads ignored local Skill, Cmd, MonsterConfig and AwakerConfig exports. Passing `--decoded-replay FILE` instead requires a decoded replay artifact and routes with that replay's embedded copies of those four catalogs. The output records which catalog source was used. It does not modify the replay index. A one-hit window needs no selector; a multi-hit window requires the hit's global index.

```powershell
node tools/build_replay_action_candidate.mjs research/observations/replay-index.json 0 > research/observations/action-0-candidate.json
node tools/build_replay_action_candidate.mjs research/observations/replay-index.json 4 --hit-index 17 > research/observations/action-4-hit-17-candidate.json
node tools/build_replay_action_candidate.mjs research/observations/replay-index.json 4 --hit-index 17 --decoded-replay research/observations/decoded.json > research/observations/action-4-hit-17-native-candidate.json
```

The adapter derives the played card, its serialized owner and arguments, the same-camp player, hit target UID, target BattleTag, active states, skill tags, selected command and one eligible Active-damage row. It uses the reconstructed damage-input property maps at the matched hit rather than the earlier card-use maps. This allows recorded BeforeUseCard and other pre-hit property/state changes to enter the formula without simulating or guessing them.

Conditional row selection and numeric parameters may read captured `CmdCaster`, `PlayerRole`, `UpperTarget`, `OwnerCard`, or `CurCard` state layers, Awakener potency/breakthrough, their live property maps, configured team-school counts, and `math.ceil`/`math.floor`. `GetAwakerCountBySchool` follows the PvE client rule: it counts every captured Awakener role whose `AwakerConfig.School` matches, without filtering by camp. Lua-style comparison, `not`, `and`, and `or` are accepted inside numeric parameters while the final value must remain finite and numeric. Every ordinary Active row is evaluated and exactly one must match both its condition and the chosen target. Unresolved functions or variables fail. The output retains the condition trace, target match, school counts, and chosen row. `UpperTarget` requires a matching recorded target-selection command; automatic `FrontEnemy`, `RandomEnemy`, and `AllEnemy` selectors use the matched hit target as retrospective identity evidence. `MaxHpEnemy`, `MinHpEnemy`, `MaxHpAndBlockEnemy`, and `MinHpAndBlockEnemy` are reconstructed from all captured living enemies and must select the recorded target under the original first-in-registry tie behavior.

For a stored main-target command, the adapter requires exactly one earlier `BESetTempMainTarget` using one of those scalar HP selectors. It identifies played-skill hits from explicit replay caster and skill IDs, requires the first action-window hit to belong to that played skill, and reconstructs the stored target from the first complete played-skill hit boundary before any action damage. A chosen `TempMainTarget` hit must equal that UID; an `AllEnemyWithoutMainTarget` hit must be another enemy that was alive at selection time. This preserves the stored selection when the main target's HP changes before later hits. If the command's optional passive-damage condition is true, the candidate still rejects because the ordinary and passive main-target hits cannot yet be separated safely.

`IsSuperUtlSkill()` is resolved from the captured caster properties. The adapter follows the client rule that a positive `ulti_skill_level_up` forces Super Ultimate; otherwise `doubleUltiEnergy` must be true and current `ulti_energy` must meet the rounded maximum derived from `ulti_energy_max`, its percentage/flat cost modifiers, and `ulti_energy_max_per`. The derived maximum, inputs, and decision are retained in `superUltimateResolution` for review.

`BattleUnitBase:BeHit` mutates block and HP before it calls `BattleRecord:OnBeHit`. The chronological index therefore restores the target's damage-input HP from `beHitConfig.oldHp` and its block from the post-event property value plus `beHitConfig.blockLose`. Other role/card properties and active states use the latest values recorded before `BeHit`. Missing reconstruction fields mark the hit boundary incomplete.

The adapter also recognizes a single `BEActiveDamage.State` row. Its nine-parameter command supplies the ordinary Active base, repetition, subtype and flat argument; the attached state grant is reported separately and excluded from the selected pre-hit calculation. In the recovered original effect, `Damage2SingleTarget` calls `BeHit` before creating that state effect. The state amount, later hits and encounter outcome remain outside this boundary. One previously decoded Chapter 1-7 replay now yields a deterministic certain-critical pre-hit regression of 75 against a recorded 75. The recorded engine-code version is unknown, and this outcome-first check receives no holdout credit; see `research/evidence/state-attached-active-replay-regression-20260923.json`.

The supported output boundary remains intentionally narrow: one selected hit from one Awakener-owned card against one enemy monster, exactly one eligible ordinary `BEActiveDamage` row, and no nonzero damage subtype. Captured card argument tables may carry the replay's `n = numeric-item-count + 1` Lua cursor. Positive repeated-hit counts are supported when exactly one enemy is alive and the matching direct-hit count is a positive multiple of the configured repetition count. The output records the hit ordinal, execution ordinal, and total matched hits; trigger-graph review is still required when several executions share one card/skill identity. Other command rows may be present because their recorded effects are already reflected in the damage-input snapshot. A nonordinary damage row is tolerated only when it has a fully resolved condition that evaluates false at the captured hit boundary; an eligible, unconditional, or unresolved competing damage path is rejected. The result retains those condition traces. `PerformTarget` is accepted only for the inspected `CmdTarget` and `EnemyFieldCenter` presentation paths; it does not replace the effect's combat `Target`. Ambiguous ownership, targets, hits, command routing or configuration fail instead of selecting a convenient interpretation.

If critical chance depends on RNG, the result has status `PREOUTCOME_INPUT_REQUIRED` and no calculation. `--crit-roll N` accepts a 1-100 pre-outcome critical roll. For publication or holdout use, that roll must be independently captured. The recovered replay's 751 noncritical and 2,028 critical exact checks use explicit branch-extreme rolls chosen after viewing the outcomes; they are retrospective branch consistency checks and receive no holdout credit.

The observed `BeHit` record is copied into a separate output field and is never read to construct the scenario. After the calculation exists, `comparison` reports predicted `preHitDamage` against `beHitConfig.castDamage`; this is the pre-shield incoming damage carried into `BeHit`, not HP lost. Every output remains a retrospective regression candidate. A human must still review the action window for triggered or overlapping actions. An already viewed replay can never become a blind holdout, and no candidate is publication evidence until the observation audit accepts its provenance and comparison.

The current 42-record regression corpus contains 23 Player-only records and 19 mixed-domain records. The Player-only records contribute zero candidates; all 428 candidates are selected Monster hits from the mixed records and pass the adapter's Monster-target requirement. This establishes only the provenance of narrow verification regressions. It does not classify any whole mixed record as PvE and provides no budget, cheese, theorycraft, blind-holdout or publication claim. The sanitized routing summary is `research/evidence/replay-regression-domain-routing.json`.

## Static command coverage

`node tools/audit_replay_candidate_rows.mjs` regenerates the source-hashed `research/evidence/replay-candidate-row-audit.json`. It excludes skills explicitly marked `IsPVP: true`, then follows Skill-to-Cmd links for skills with an Awakener owner and one of the adapter's supported tags. The current export has 296 such non-PvP skills linked to 263 commands. All 121 linked commands containing ordinary Active damage pass the current static command-shape checks; all 149 ordinary Active rows, including 54 conditional rows, have compatible individual syntax. A competing nonordinary damage path is statically compatible only when every such row has a condition the adapter can resolve; the captured runtime condition must still prove each path inactive. Stored main-target rows count as compatible only when a unique earlier `BESetTempMainTarget` uses a supported scalar HP selector.

These numbers do not mean 121 commands are executable or accurate. The audit does not know runtime variables, which conditions pass, actual hit count, target identity, property completeness, critical RNG, triggers or gameplay outcomes. It only measures whether a future complete replay boundary could reach the adapter without a known static row-shape blocker.

Command `131035` is the stored-main-target coverage case. Its `BESetTempMainTarget` row selects `MaxHpEnemy` and stores the first selected role in the command member `TempMainTarget`. The next potency-dependent ordinary row attacks that main target, another ordinary row attacks `AllEnemyWithoutMainTarget`, and a later condition can add passive damage to the main target. Original `BESetTempMainTarget:DoEffect` stores the first resolved target or nil; the parser's two selectors read that same member and exclude the identical role object. The adapter now preserves selection-time state and associates a caller-selected replay hit by target membership. It requires the recorded hit to carry the played card owner's caster identity and the played skill identity; missing identity is rejected rather than inferred from the surrounding action window. It also rejects an active optional passive path, incomplete hit boundaries, a prior unrelated hit, unsupported setup rows, or ambiguous row matches. This closes the static shape gap without claiming that an actual Mosk replay has passed.
