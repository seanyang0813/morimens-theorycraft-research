# Local replay recovery checkpoint

The source-derived server-to-file dependency is documented in [`REPLAY_ACQUISITION_PATH.md`](REPLAY_ACQUISITION_PATH.md). A player UID first yields a CopyReview record-ID queue; a selected record then yields a battle UUID, and the client asks for an OSS header and object name before downloading the replay container. The repository does not store the player UID, battle UUID, object name, or authentication material.

The read-only inspection in `research/evidence/local-replay-storage-inspection.json` checked the installed game's BattleLog directory, the Morimens LocalLow directory, and replay/record-named JSON/text/log/data candidates under BattleLog and `_game_data_`. BattleLog was empty and no named replay candidates were found. The two Unity logs had no matches for `BattleReplayData FirstRecord`, `copyProperties`, `recordZips`, `compStr`, or `occupation_master`. Log hashes and exact checked paths are recorded without copying log contents into the website.

Original `BattleReplayPlayer.LoadFromLocalFile` accepts an explicitly supplied file path. `DealReplayContent` decodes JSON, decompresses `compStr` with the client LZ4 module, unpacks it with cmsgpack, and decompresses/unpacks each `recordZips` entry. It keeps the result in replay-player fields. The inspected download/playback methods do not automatically save a replay file. `SaveRecordList` populates an in-memory field despite its name; it is not a disk writer.

An explicitly authorized live-client check recovered one high-difficulty replay container. A narrowly scoped read-only runtime search for the already selected battle UUID exposed the client-resolved object name; that object was retrievable without replaying credentials. The original bytes, decoded payload, index, screenshots and identifiers remain in ignored private directories. Public artifacts retain only neutral observation labels, aggregate counts, and cryptographic hashes.

Three batch passes searched only replay object names and battle-record UUID fields already loaded by explicitly authorized public profiles. They found fourteen additional valid containers, including four records loaded together from a second profile's Frenzy and difficult H3 history. The containers decode to 3,913 records, 108,931 events, 791 card-use boundaries and 1,105 hits, with no unknown command or event IDs. One replay exposed and now tests empty property maps after `ChangeCardId`. The sanitized public manifest is `research/evidence/replay-batch-recovery.json`; raw containers, decoded state, object names and player identifiers remain private.

`tools/decode_battle_replay.py` provides an offline path for an explicitly supplied replay JSON file. It calls the copied PC client's exported `luaopen_lz4` and `luaopen_cmsgpack` implementations directly, expands the outer `compStr`, expands every `recordZips` entry, converts the result to reviewable JSON, hashes the original input, and refuses to overwrite its output. Decoded artifacts must remain under ignored `research/observations/` because replays can contain player and build data. The CLI separately requires the caller to choose the JSON-container byte encoding (`utf8` or `latin1`) and the `compStr` string-to-byte convention (`latin1`, `utf8`, or `base64`); it does not silently try alternatives. The first recovered server container is binary JSON: the JSON document and `compStr` both require the explicit `latin1` choices. Native decoding and indexing results are recorded separately from gameplay-formula validation.

`research/evidence/replay-protocol.json` freezes 29 command IDs and 101 render-event IDs enumerated from the original client tables. `tools/index_decoded_replay.py` uses that catalog to preserve initialization snapshots and every chronological event, with dedicated lists for property changes, state changes, card uses and hit results. It applies absolute property-change values, card replacements, state lifecycle changes, argument updates and role spawning/removal in frame order. Each `UseCard` boundary receives a full copy of the known role, card and active-state maps after energy payment and before `BeforeUseCard` triggers, matching the recovered client order. Unknown or unbound mutations mark the boundary incomplete instead of being ignored.

The recovered replay decodes to 165 records and indexes to 4,046 render events, 32 card uses, and 68 hit records with no unknown command or event IDs. The index preserves nested `rd_CommandResult` records. Each card-use snapshot gets a chronological window ending immediately before the next `UseCard`, with the window's render events, nested command results, `lg_SelectTargets` records and `BeHit` events attached. Properties serialized immediately before `AddNewCard` are staged and applied when the card arrives; presentation events may retain nonobject payloads losslessly. All 32 card-use boundaries are complete. Triggered actions and overlapping timelines still require review.

The index now also freezes a damage-input snapshot for every `BeHit`. The original hit path records property changes before the `BeHit` render record, so the index restores target HP from `oldHp` and target block from the current value plus `blockLose`; all other properties and active states use the latest recorded values at that boundary. This preserves recorded pre-hit trigger changes without treating post-hit HP/shield as formula inputs.

`tools/build_replay_action_candidate.mjs` performs the first fail-closed binding for a narrow direct hit. With `--decoded-replay`, it reads Skill, Cmd, MonsterConfig and AwakerConfig rows embedded in that replay instead of borrowing current-client rows. It joins one complete card-use boundary and its reconstructed damage-input snapshot to the serialized card owner and arguments, same-camp player, hit monster, target BattleTag, active states, skill tags and exactly one eligible Active-damage row. It accepts the replay's one-past-end Lua argument cursor and validates repeated damage rows against complete one-enemy hit groups. Conditional rows and numeric parameters can read captured state layers, potency/breakthrough and live role/card properties; every unresolved binding or competing damage path fails. One recovered Mouchette action produces exact 751 noncritical and 2,028 critical branch checks from replay-native catalogs. Across the fourteen-record batch, 122 deterministic Active-hit candidates match exactly with zero mismatches, and all 56 chance-dependent candidates match one of the independently evaluated roll-1 and roll-100 branches. The four newest higher-difficulty records add 40 complete hit snapshots but no action passes the current narrow adapter. Thirteen branch cases are in two other records from the same stage as the Mouchette case. Outcomes were recovered before calculation, so none is an independently frozen holdout. See `docs/REPLAY_ACTION_CANDIDATE.md`.

Source inspection establishes that the first `rd_InitBattle` command carries full `roleDataList`, `monsterDataList`, and `cardDataList` snapshots. Later record frames include absolute property values, state additions/layer changes/removals, card use, target selection, and hit results. This makes an exported replay materially stronger than screenshots for reconstructing a regression case. A blind holdout still needs a deterministic crit path or pre-outcome RNG evidence because the recorded `isCrit` result is an outcome.

Very long battles can produce research indexes larger than JavaScript's maximum
string size because full event windows are retained for forensic work.
`tools/compact_replay_candidate_index.py` rebuilds the index from the decoded
private replay and writes only the action, hit, snapshot, role, card, state and
target-selection fields read by the strict candidate adapter. The compact file
remains under `research/observations`; it retains outcomes for retrospective
auditing and therefore cannot be treated as a blind holdout.

For later replay captures, preserve the original bytes and hash before decoding. Verify the client's binary-string and LZ4 conventions against those bytes rather than assuming base64 or a standard LZ4 frame. Extracted outcomes from already viewed replays can support regression validation but cannot retrospectively become blind holdouts. Embedded resource rows remove dependence on current data tables for each routed action, but the recovered battle data has no explicit engine-code version, so strict historical runtime compatibility still requires evidence review.
